# 门禁与目录

## 一、目录：按需创建

### 1.1 需要 `docs/` 吗

**同一类型超过 1 份才建目录。**

| 规模 | 布局 |
|---|---|
| 契约 1 份 + 参考 ≤1 份（最常见） | 全放根目录：`AGENTS.md`、`CHANGELOG.md`、`spec.md` |
| 契约 ≥2 份 或 参考 ≥2 份 | 建 `docs/`，按内容类型分子目录 |
| 有必须留档但不维护的东西 | 才建 `docs/archive/` |

根目录放「每次开工都会用到」的东西。为 1 份 spec 建 `docs/`，等于要求每个新人先学「为什么它在那儿」。

### 1.2 完整结构

```
AGENTS.md                 ← 根：agent 每次开工读
CHANGELOG.md              ← 根：发版时读
spec.md                   ← 契约（1 份）
docs/
  contracts/              ← 契约（≥2 份时）
  reference/              ← 参考
  archive/                ← 只读，默认不存在
.agents/
  MEMORY.md               ← 系统自管（唯一进 git 的）
  work/
    BOARD.md              ← 看板
    wip/                  ← 挂起/进行中，删前必须蒸馏
    scratch/              ← 草稿/方案/分析，随时可清空
```

**`living / reference / archive` 是头注里的 `类型:` 字段，不是文件夹名。** 目录按内容类型分，两类维度混用会得到 `contracts/ reference/ archive/` 这种一半内容一半生命周期的怪结构。

### 1.3 三条硬规则

- **空目录是罪**——它会邀请人往里塞东西。
- **不要按 PARA 建四层**（Projects/Areas/Resources/Archives）：`Projects` 由任务板承担，`Archives` 由 git 承担。
- **目录结构不需要文档说明**（会腐化）；需要的是每份文件自己的头注。

## 二、门禁清单

| # | 检查 | 判据 | 失败时 |
|---|---|---|---|
| 1 | 文件白名单 | 仓库内受版本控制的 `*.md` ⊆ 允许清单 | 红 |
| 2 | 头注完备 | **仅契约 / 参考类**：`类型:`、`读者:`、`更新触发:`、`规模上限:` | 红 |
| 3 | 头注取值 | `规模上限:` ∈ {契约 300, 规范 400, 参考 600} | 红 |
| 4 | 必填章节 | `契约`→三节；`规范`→有一个含「验收」的章节；`参考`→不强制 | 红 |
| 5 | 参考类时效 | 有 `采集日期:`；超过 180 天 | 缺则红 / 超期告警 |
| 6 | CHANGELOG 结构 | 含 `## [Unreleased]`；标题匹配 `^## \[x\.y\.z\] - \d{4}-\d{2}-\d{2}( \[YANKED\])?$`；类别只有官方六类 | 红 |
| 7 | **锚点存活** | 契约里每个锚点能 grep 到 | 红 |
| 8 | **引用可达** | AGENTS 文档地图里列的路径、md 相对链接都存在 | 红 |
| 9 | 零行号 | 禁止 `file.ext:123` / 「第 N 行」 | 红 |
| 10 | AGENTS 体量 | > 100 行 | 告警 |
| 11 | 文档体量 | 超头注声明的档位 | 告警 |

### 2.1 三条最容易写错的

**白名单必须排除 `.agents/**` 与所有 gitignored 路径。** 否则 `scratch/` 里的草稿会被判红，等于 scratch 不可用——这是这类门禁最常见自伤。

**AGENTS.md 与 CHANGELOG.md 豁免头注检查。** 它们有各自的固定形状，硬塞 `类型:` 只会让模板变丑。

**第 7、8 道闸是这个体系唯一的「内容真实性」检查。** 其余各条都只查结构——文档可以结构完美而内容全假（代码改成 32px 了，文档还写 28px）。锚点 grep 不到就报红，是防止「门禁全绿、文档全假」的唯一手段。

### 2.2 判红 vs 告警

- **判红**：结构缺失、矛盾、越界——有唯一正确答案。
- **告警**：体量、时效——「该去看一眼」，处置取决于上下文（合并？迁出？重采？）。

一旦「长度超标」判红，达标手段必然退化成删掉最长的边缘条件——而那恰恰最不可再生。

## 三、门禁自身的验证

改门禁的人不能让门禁自证。每加一道闸，在独立工作树上做四次破坏性验证：

```bash
git worktree add /tmp/gate-probe -b probe/gate
cd /tmp/gate-probe
# 1) 放一个不在白名单的 md（含未跟踪的）→ 必须红
# 2) 把白名单里的文件改名 → 必须红，且报「缺失或改名」而非「读不到文件」
# 3) 改一个被判据约束的值 → 对应闸必须红
# 4) 改掉使数字不一致的引用 → 对应闸必须红（证明它不是恒真）
git worktree remove /tmp/gate-probe
```

把这四次写成 `npm run check:selftest`，否则它一定退化成「跑一次绿就交」。

## 四、与人的协作

- **删文档需要人确认**：agent 可以列清单、可以提议，但不自行删一份别人可能在读的文档。
- **白名单变更 = 一次人工审查**：新建文档必须同批改白名单，这个摩擦是特性不是缺陷。
- **失败时不许绕过**（`--no-verify`、注掉检查）——绕过一次就永久失效。
