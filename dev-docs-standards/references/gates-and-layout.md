# 门禁与目录

## 目录

- 一、目录：按需创建（何时建 `docs/`、完整结构、三条硬规则）

## 一、目录：按需创建

### 1.1 需要 `docs/` 吗

**同一类型超过 1 份才建目录。**

| 规模 | 布局 |
|---|---|
| 契约 1 份 + 参考 ≤1 份（最常见） | 全放根目录：`AGENTS.md`、`CHANGELOG.md`、`spec.md` |
| 契约 ≥2 份 或 参考 ≥2 份 | 建 `docs/`，按内容类型分子目录 |
| 有必须留档但不维护的东西 | 才建 `docs/archive/` |

根目录放「每次开工都会用到」的东西。为 1 份 spec 建 `docs/`，等于要求每个新人先学「为什么它在那儿」。

### 1.2 完整结构

```
AGENTS.md                 ← 根：agent 每次开工读
CHANGELOG.md              ← 根：发版时读
spec.md                   ← 契约（1 份）
docs/
  contracts/              ← 契约（≥2 份时）
  reference/              ← 参考
  archive/                ← 只读，默认不存在
.agents/
  MEMORY.md               ← 系统自管（唯一进 git 的）
  work/
    BOARD.md              ← 看板
    wip/                  ← <ID>-<slug>.md，删前必须蒸馏
    scratch/              ← 草稿/方案/分析，随时可清空
```

**`living / reference / archive` 是头注里的 `类型:` 字段，不是文件夹名。** 目录按内容类型分，两类维度混用会得到 `contracts/ reference/ archive/` 这种一半内容一半生命周期的怪结构。

### 1.3 三条硬规则

- **空目录是罪**——它会邀请人往里塞东西。
- **不要按 PARA 建四层**（Projects/Areas/Resources/Archives）：`Projects` 由看板承担，`Archives` 由 git 承担。
- **目录结构不需要文档说明**（会腐化）；需要的是每份文件自己的头注。

## 二、门禁清单

| # | 检查 | 判据 | 失败时 |
|---|---|---|---|
| 1 | 文件白名单 | 仓库内受版本控制的 `*.md` ⊆ 允许清单 | 红 |
| 2 | 头注完备 | **仅契约 / 参考类**：`类型:`、`读者:`、`更新触发:`、`规模上限:` | 红 |
| 3 | 头注取值 | `规模上限:` ∈ {契约 300, 规范 400, 参考 600} | 红 |
| 4 | 必填章节 | `契约`→三节；`规范`→有一个含「验收」的章节；`参考`→不强制 | 红 |
| 5 | 参考类时效 | 有 `采集日期:` + `来源版本:`；采集超过 180 天 | 缺则红 / 超期告警 |
| 6 | CHANGELOG 结构 | 含 `## [Unreleased]`；标题匹配 `^## \[x\.y\.z\] - \d{4}-\d{2}-\d{2}( \[YANKED\])?$`；类别只有官方六类 | 红 |
| 7 | **锚点存活** | 契约里每个锚点能 grep 到 | 红 |
| 8 | **引用可达** | AGENTS 文档地图里列的路径、md 相对链接都存在 | 红 |
| 9 | 零行号 | 禁止 `file.ext:123` / 「第 N 行」 | 红 |
| 10 | AGENTS 体量 | > 100 行 | 告警 |
| 11 | 文档体量 | 超头注声明的档位 | 告警 |
| 12 | 工作现场一致性 | 看板两表列名 / ID 词表 / 取值 / 依据坐标 / wip 双向绑定（见 §2.3） | 红（目录不存在则跳过） |
| 13 | README 体量与描述 | ≤120 行；简短描述逐字等于 `package.json` 的 `description` | 告警 |
| 14 | 计数与承诺词 | 不出现手写的会变计数（`\d+ 条用例` / `共 \d+ 例` / `共 \d+ 行`）；「后续版本 / 以后会 / 即将」必须带看板 ID | 红 |

### 2.1 三条最容易写错的

**白名单必须排除 `.agents/**` 与所有 gitignored 路径。** 否则 `scratch/` 里的草稿会被判红，等于 scratch 不可用——这是这类门禁最常见自伤。

**AGENTS.md 与 CHANGELOG.md 豁免头注检查。** 它们有各自的固定形状，硬塞 `类型:` 只会让模板变丑。

**第 7、8 道闸是这个体系唯一的「内容真实性」检查。** 其余各条都只查结构——文档可以结构完美而内容全假（代码改成 32px 了，文档还写 28px）。锚点 grep 不到就报红，是防止「门禁全绿、文档全假」的唯一手段。

### 2.2 判红 vs 告警

- **判红**：结构缺失、矛盾、越界——有唯一正确答案。
- **告警**：体量、时效——「该去看一眼」，处置取决于上下文（合并？迁出？重采？）。

一旦「长度超标」判红，达标手段必然退化成删掉最长的边缘条件——而那恰恰最不可再生。

### 2.3 工作现场门禁（看板 + wip）

工作现场不入库（`.agents/work/` 被 gitignore），所以**存在即校验、不存在即跳过**——但跳过条件必须窄：

- 只有 `.agents/work/` **整个不存在**才 skip（新克隆）；**目录在、`BOARD.md` 不在 ⇒ 红**（板被删或被挪走，是事故不是干净）。
- 列语义见 [parallel-work.md](parallel-work.md) 的「看板 schema」；门禁只管**每一格能不能被证明**：
  - `ID` 在词表内、跨两表不重复；`P` / `状态` 在枚举内；`最后动` 是日期。
  - `下一步` 非空、不含「同上 / 待定 / 看情况 / 继续优化」。
  - `依据` 逐个坐标核：`docs/…md §x.y` 的标题要 grep 到、`AGENTS.md 硬约束 N` 要命中 `^N. **`、任何 `.agents/…` 路径要存在、7–40 位 sha 要 `git cat-file -e`（非 git 环境降级为告警）。
  - 已完成表的 `commit` 也验存在性——否则 `deadbeef` 是绿的，而依据里的 sha 却查，前后不对称。
  - 板说「进行中 / 挂起」必须有 `wip/<ID>-*.md` 且头部状态逐字一致；`wip/` 里每份都要在板上有同 ID 的行。
- 体量只告警（待办 >12 行 / 全文 >70 行），不判红。
- 归档区（`BOARD-archive.md`）与活跃区同一套列语义：固定表头、时间倒序、短 sha 存在、ID 跨两文件唯一，且**首行不得新于活跃区末行**——否则说明抽的不是尾部，历史顺序会错。

**每个门禁都要有一条「在真实树上跑一遍」的用例。** 夹具全绿、真仓红，是结构解析型门禁最典型的假安全：夹具是作者按自己的理解写的，共享同一个误解。

**结构解析型门禁的四个必测破坏**（每缺一个就留一个静默洞）：

1. **缺分隔行**——解析器常把第一行数据当分隔行吃掉，那行不经任何规则却 exit 0。
2. **切格与转义**——`split('|')` 不认 `\|`；头注一旦写了「用 `\|` 转义」，文档与实现就互斥、照文档写必红。要么实现认转义，要么别写这条约定。
3. **非文件条目**——`readdirSync` 不筛类型时，`wip/U1-x.md/` 这种「以 `.md` 结尾的目录」会让读取抛 `EISDIR`，stdout 一行 `RED` 都没有、只有栈。
4. **skip 边界**——只有「整个目录不存在」能 skip；父目录在就该红。

### 2.4 可选的「依赖式新鲜度」（只告警）

把文档里点名的源文件当依赖：用 `git log` 问一句「这个文件在文档最后一次修改之后被改过吗」，被改过就提示复查。它抓的是「代码动了、文档没动」，成本低、不需要注解。

只做告警：判红会逼人删掉最该保留的细节，或者在每次改代码时无意义地摸一遍文档。

## 三、门禁自身的验证

改门禁的人不能让门禁自证。每加一道闸，在独立工作树上做四次破坏性验证：

```bash
git worktree add /tmp/gate-probe -b probe/gate
cd /tmp/gate-probe
# 1) 放一个不在白名单的 md（含未跟踪的）→ 必须红
# 2) 把白名单里的文件改名 → 必须红，且报「缺失或改名」而非「读不到文件」
# 3) 改一个被判据约束的值 → 对应闸必须红
# 4) 改掉使数字不一致的引用 → 对应闸必须红（证明它不是恒真）
git worktree remove /tmp/gate-probe
```

把这四次写成 `npm run check:selftest`，否则它一定退化成「跑一次绿就交」。

还有一层：**谁写的门禁，就不能是唯一写夹具的人。** 同一人写的夹具与实现会共享同一个误解——实测过 19 例自测全绿，另一个人按规格重写 94 例，立刻抓出两条实现缺陷（缺分隔行吞首行、`.md` 目录崩栈）。`check:selftest` 只证明「按作者的理解是对的」。

## 四、与人的协作

- **删文档需要人确认**：agent 可以列清单、可以提议，但不自行删一份别人可能在读的文档。
- **白名单变更 = 一次人工审查**：新建文档必须同批改白名单，这个摩擦是特性不是缺陷。
- **失败时不许绕过**（`--no-verify`、注掉检查）——绕过一次就永久失效。
