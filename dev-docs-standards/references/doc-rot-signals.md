# 文档腐化信号（收尾审计用）

结构门禁查不出「结构完美、内容已在撒谎」。这份清单是收尾 / 发版前的**审计项**，按「出现频率 × 危害」排序——命中任何一条，都说明某个容器缺位。

| # | 信号 | 长什么样 | 怎么发现 | 修法 |
|---|---|---|---|---|
| 1 | **两处真相、没有标记** | 同一份文档同时描述旧流程与替代方案，不标哪个是现行 | 搜「不再 / 已改为 / 原…现…」 | 删旧的，只留现行；旧行为归 commit message |
| 2 | **手写计数漂移** | `646 条用例`、`最老的 17 行`、`上限 134000` | 数字 vs 实际输出 | 删数字，或改由脚本生成 / 门禁回读 |
| 3 | **没主体的将来时** | `后续版本会补`、`以后支持` | grep 承诺词 | 补看板 ID，否则删 |
| 4 | **指针指向已删改名** | 契约里的路径、类名、键名 | 门禁「引用可达」+ grep | 改指针；删文件时同批改引用 |
| 5 | **同一规则三处各写一份** | AGENTS 硬约束、契约、README 各有一段 | 搜规则关键词 | 留被 review 的那份，其余改成指针 |
| 6 | **时间词** | 「本轮」「目前」「暂时」 | grep | 改成可判定的现状描述 |
| 7 | **日期新、内容旧** | `采集日期` 很新，外部产品早升级了 | 来源版本 vs 实际版本 | 整份重采，不在旧表上打补丁 |
| 8 | **过程叙述留在契约** | 「Round 23 改成…」「U18 之后…」 | grep 版本号 / 任务 ID / 「终于」 | 压成口径，过程归 CHANGELOG 与 commit |
| 9 | **摘要与正文打架** | 文件头或 README 的摘要 vs 正文 | 抽查摘要里的名词 | 摘要只写指针，不复述结论 |
| 10 | **只增不减** | 同一小节连续多轮编辑只有新条目，没有修订或删除 | `git log -p` 看该节改动 | 合并、改写或迁出；`## 条款` 尤其危险 |

## 什么时候跑

- 每个迭代收尾、发版前；
- 改完一份契约（顺手看第 1、4、5 条）；
- 外部依赖升级后（第 7 条）。

## 哪几条能交给门禁

2（G14 计数正则）、3（G14 承诺词）、4（G8 引用可达）、7（G5 `采集日期` + `来源版本`）。**其余六条只能靠 review**——所以它们必须落在**会被 review 的容器**里，而不是 agent 记忆。

## 可选：依赖式新鲜度

把文档里点名的源文件当依赖，用 `git log` 问一句「这个文件在文档最后一次修改之后被改过吗」，被改过就提示复查。它抓的是「代码动了、文档没动」，成本低、不需要注解。**只做告警**：判红会逼人删掉最该保留的细节，或者在每次改代码时无意义地摸一遍文档。
